# 扫描相机：项目现状与后续开发入口

梳理日期：2026-11-02。依据当前源码、构建配置、现有正式 APK 和本轮构建结果。
本轮新增此文档，未修改功能源码、签名配置或现有正式 APK，未移动或删除文件。

## 1. 当前项目是什么

- 原生 Android 应用，应用名「扫描相机」，包名 `com.scan.camera`。
- 当前源码版本：`2.3.0`，`versionCode = 28`。
- Android 10（API 29）起；compileSdk / targetSdk 均为 34。
- Kotlin + XML 布局 + ViewBinding，3 个 Activity，15 个 Kotlin 文件，共约 3570 行。
- 核心依赖：CameraX 1.3.4、Material 1.12.0、离线中文 ML Kit 16.0.0、协程 1.8.1。
- 没有服务端、账号体系或本地业务数据库；设置用 SharedPreferences，页面用私有文件保存。
- 当前目录不是 Git 仓库，未发现 AGENTS.md，也没有 `src/test` / `src/androidTest` 测试源码目录。

## 4. 现有处理流程

### 拍摄

CameraX 预览 → ImageAnalysis → PageDetect → 实时框 / 自动拍摄判断。

手动快门默认连拍 3 张，按清晰度选优；自动与音量键快门走单帧。
照片先写入 `filesDir/pages/capture_时间.jpg`。

- 开启校正：CropActivity 返回选框与旋转角 → processWarpedPage → 透视变换 → 可选双页拆分 → `page_时间.jpg` → 页面列表。
- 关闭校正：当前直接把 `capture_` 文件加入页面列表，存在重启后被清理的问题。
- 自动拍摄使用连续稳定 8 帧和 2600 ms 冷却；持续时间随实际分析帧率变化，不能视为严格 0.8 秒。尚无“确认已翻到新页”的内容去重。

### 导入

系统图片选择器（单次最多 30 张）→ 复制到私有目录 → EXIF 转正及缩放 → 可选双页拆分 → 页面列表。
导入流程没有进入手动四角校正页。

### 导出

页面文件快照 → 灰度 / 黑白 / 原色 → 可选离线中文 OCR → PdfDocument 绘制图片及近透明文字层 → MediaStore 保存 PDF → 有文字时附带 TXT。

- PDF：A4 或原始比例，输出至 `Download/扫描相机/`。
- 图片导出：直接复制当前页面 JPEG；不会额外应用当前 PDF 的灰度、黑白、锐化与对比设置。
- 历史 PDF：长按「相册」访问，通过 MediaStore 查询，并支持打开、分享、删除。
- 删除页面：移入 `filesDir/trash/`，单页删除提供 Snackbar 撤销。没有独立回收站浏览界面。

## 6. 优先处理的问题

以下是源码检查结论，尚未逐项在手机上复现；编译成功和 lint 无错误不能覆盖这些行为问题。

| 优先级 | 问题及证据位置 | 影响与修复方向 |
|---|---|---|
| 高 | 关闭校正时，`MainActivity.kt:827` 的 beginCaptureFlow 直接加入 `capture_` 文件；`:1317` 的 restorePages 启动时删除全部 `capture_` 文件 | 直接拍摄的页面在重新创建主界面时可能丢失。正式入列应统一转为页面文件，并把待处理拍摄与已确认页面分开管理 |
| 高 | `MainActivity.kt:102` 的 pdfJob 始终为 null；`:397` 取消调用它；`:1094` 启动的协程未赋给该变量 | 「取消生成」无效。绑定实际任务，并补齐页间、OCR 后、写文件前的取消与清理规则 |
| 高 | `MainActivity.kt:323` 仅交换内存列表；`:1322` 恢复时按文件名排序 | 拖动页序重启后丢失。持久化稳定页面 ID 和排序，支持恢复时对账 |
| 高 | `PdfCreator.kt:79-81` 的缓存键没有实际位图尺寸，且先命中缓存再判断 recognizer 是否存在 | 同进程先开 OCR 后关闭仍可能输出文字层；切换分辨率后复用旧坐标可能导致文字层错位。关闭 OCR 时直接跳过缓存，缓存键包含实际尺寸与处理版本 |
| 高 | `MainActivity.kt:150-163` 导入拆为两页后，没有删除原先复制的 `page_...jpg` | 当次列表显示两页，下次恢复可能额外加入未拆原图。成功提交子页后移除中间文件，失败时保持原子性 |
| 中 | `CropActivity.kt:33` 通过 Images 解码并按 EXIF 转正；`MainActivity.kt:913` 正常校正分支却直接 BitmapFactory.decodeFile | 在依赖 EXIF 记录朝向的照片上，预览选框和全图坐标系可能不一致。统一解码朝向并测试 0/90/180/270 度 |
| 中 | `MainActivity.kt:793` 只防等待裁边，没有覆盖拍摄请求已提交但尚未回调的阶段；`:1335` 也未按 generating 禁用快门 | 连点、连拍、自动拍摄和 PDF 生成缺少统一互斥状态。增加明确的拍摄/处理/导出状态及按钮约束 |
| 中 | `MainActivity.kt:827` 缩略图解码、`:865` 连拍评分在主线程执行；全图处理及 OCR 存在多份位图 | 高像素照片可能卡顿或内存紧张。把解码、评分统一移到后台，明确位图归属和失败释放 |
| 中 | 页面校正后删除原图，已确认页没有重新裁边入口 | 后续做重裁、无损旋转或多种处理预览时，需要保留原图及独立编辑参数 |
| 低 | `PreviewActivity.kt:79` 提示“删除后无法恢复”，但主界面提供撤销；trash 使用原文件修改时间判定过期 | 提示与实际行为不同；旧照片删除后未必还能保留完整 48 小时。改为记录删除时间，统一提示 |

## 7. 文档与工程基础的缺口

1. README 安装文件名仍写 `扫描相机-v1.6.2.apk`，但目录实际只有 v2.3.0 正式包。
2. README 描述的实时边缘算法仍为行列游程扫描，源码已是连通域、凸包及最大面积四边形。
3. README、安全声明及构建注释中的 v3 签名描述与现有 APK 的 v2 实测结果不符。应按产物结果更新。
4. `app/build.gradle.kts` 设置 `abortOnError=false`、`checkReleaseBuilds=false`，因此将来即使有 lint 错误，构建成功也不能作为质量门槛；本轮报告实际为 0 错误。
5. 当前没有 Git 版本基线、自动化行为测试与固定真机回归清单。建立版本管理时沿用现有忽略项，另评估排除 APK 和 `.mimosa/`，保留 Gradle Wrapper。
6. 正式签名保留原证书；不同签名的 Debug 包不能直接覆盖已有正式版。后续真机开发可考虑独立 debug applicationId，避免测试时卸载正式版数据。

## 8. 建议的开发顺序

### 第一阶段：稳定现有扫描流程

优先修复页面文件归档、取消生成、页序持久化、OCR 缓存和双页导入中间文件；随后核对 EXIF 坐标和拍摄互斥。
修复后至少回归：关闭校正拍摄再重启、拖动页序再重启、导入 12 张保持顺序、拆页后重启、OCR 开→关、2400→3200 分辨率切换、取消生成、连续快门、横竖朝向与超大图。

### 第二阶段：拆分职责

不需要先大规模重写。逐步从 MainActivity 提取：

- 页面存储层：稳定 ID、原图/处理图、顺序、删除时间、恢复和回收站。
- 相机控制层：绑定、变焦、对焦、快门、连拍和自动拍摄状态。
- 图像处理层：解码朝向、裁边、旋转、双页拆分及增强管线。
- 导出层：PDF / TXT / 图片统一任务、进度、取消和结果。

MainActivity 最终保留 UI 事件和状态展示；后续可以逐步引入 ViewModel，按实际需要选择文件清单或 Room。

### 第三阶段：增加功能

基础稳定后，再按使用需求选择：文档/章节管理、已拍页面重新裁边、增强效果实时预览、批量旋转、可浏览回收站、OCR 文本校对或更可靠的翻页自动拍摄。
目前代码规模适合渐进迭代，可以保留 Kotlin、CameraX 和现有离线处理路线。
