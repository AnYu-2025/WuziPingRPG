## 1. 目标（一句话）

> 让**真实照片**成为一等公民：EXIF 朝向由**内核**决定而不是浏览器默认，
> 编辑栈能存成**工程文件**跨会话恢复，无头链路**吃得下 JPEG**，
> 大图交互**真的用得上缓存**——然后才谈第三端。

### 3.2 序 1 · g3 元数据与朝向（**本轮内核核心增量**）

**做法**

- 新增 `packages/core/src/metadata/`：纯 TS、零依赖、`lib: ES2022` 无 DOM——
  读 TIFF/EXIF 头（`II`/`MM` 两端序）、IFD0 + Exif SubIFD，**只取白名单字段**：
  `orientation(1..8)` · `make` · `model` · `dateTimeOriginal` · `exposureTime` · `fNumber` · `iso` · `focalLength`。
  未知 tag / 厂商私有段 / GPS / 缩略图 **一律忽略**，忽略 ≠ 谎报。
- 解析失败与"无 EXIF"是两种状态，都要能被界面区分显示；**绝不因缺元数据而改变像素**。
- **朝向（D13，落点在实施时修订）**：像素由内核 `pixels.applyOrientation(buf, o)` 在**导入那一次**置换为
  显示态，宽高互换仍只走 `rotatedSize` 唯一入口（`orientedSize` 内部调它）。旋转与镜像的组合由表驱动，不写分支特例。
  - 为什么不是"折进 `buildPlan` 的逆仿射"（原文方案）：拼图 / 切图 / 缩略图不经过 raster 阶段，
    折进仿射就要在四处各补一遍朝向 —— 病根 1 的复发形态。置换一次 ⇒ 四条路天然同源，且置换零插值、无损。
  - 由此得出两条**必须钉住**的语义：`SourceRef.width/height` = **显示态**尺寸；
    `SourceRef.exifOrientation` = **来源记录，渲染不读**（读了 = 双重旋转）。X5 的第二半就是验这条。
  - 代价：非 1 朝向多一次全尺寸拷贝，只发生在导入，不进预览循环。
- **必堵的坑**：`createImageBitmap` 默认会自己转（G2）。接内核朝向的同时**必须**改成
  `createImageBitmap(blob, { imageOrientation: 'none' })`，否则浏览器转一次、内核再转一次 = **双重旋转**。

**实施中得到的两个事实**（值得复述，否则会再踩）

- 置换表第一版把 6 与 7 的镜像分量写反了 —— 抓它的是"与 `rasterize` 在 1:1 时逐字节相等"那条 parity，
  不是任何一条手工期望。**parity 断言的价值就在这儿**：它对照的是渲染器自己的几何，而不是作者的记忆。
- `orientedSize()` 必须是 `applyOrientation` 决定输出宽高的**唯一**途径。若两端各算一次
  （一次经 `rotatedSize`、一次硬编码 `if (o >= 5)`），那么 90/270 的换轴规则会在两处漂移，
  表现为"文档尺寸与实际像素差一维"—— 这类错不会崩，只会让裁切框与拼图格子悄悄偏。

**与 §7 那条风险口径的偏差（不藏着）**：风险表写的是"单元用例喂真机图，不构造理想头"，
本轮实际是**手写构造**的 TIFF/APP1/`eXIf` 样本（结构合法、字段齐全，但都是理想头）。
真机原图这一轮没有可吃的 JPEG 解码器，因此这条风险的覆盖要等序3 —— 届时若真图让解析器出错，
**改的必须是解析器，不是样本**。

### 3.3 序 2 · d1 工程文件 + #4 自定义预设（同一条管道）

**为什么一起做**：两者缺的是同一件东西——**壳侧的读写管道**（主进程文件对话框 + IPC + 落盘位置）。
分开做会写两遍管道，而且 #4 是台账上唯一真实的壳缺口。

- **内核**（`photo.doc/v1`）：`serializeDocument(doc)` / `parseDocument(json)`。
  与 `preset-share.ts` **同构的双防线**（D14）：结构错 → 抛 `DocumentParseError`（写错了要吵）；
  数值错 → 复用 `sanitize*` 收敛（绝不静默碎图）。**只存源图引用**（path/名/字节数/指纹），不嵌 base64。
- **源图身份核验**：打开工程时按指纹/尺寸比对，不符要**明说哪张对不上**，
  沿用 sanitize 的既有立场——源图是**实体**，缺失就诚实报缺，**不伪造 1×1 幻影**。
- **壳**：「保存工程 / 打开工程」，preload 白名单按最小面扩展（当前 4 个方法），主进程仍不含内核代码（D11）。

### 3.4.2 插单 · 应用图标「月相」（台账外，用户提出）

### 3.4.3 序 3.5 · JPEG 解码搬进渲染 Worker（还序3 认下的那条代价）

**来处**：就是 §3.4 "已知代价"第二条点名的正解。序3 把桌面 JPEG 解码改走内核之后，
24 MP 的同步解码（本机合成码流 ≈ 2.9 s）发生在**界面线程**上 —— 导入一张手机直出的
大图，整个窗口在那几秒里不响应。这一片只解决"在哪条线程上跑"，不改一个像素。

**做法**：不新开第二条 Worker，而是给已有渲染 Worker 加一条 `decode` 请求。
理由是导入与渲染天然有序（先解出像素才谈得上渲染），复用同一条通道就复用同一套
握手 / 降级 / 生命周期；另起一个解码 Worker 要再多一次握手和一条独立的降级路径，
换来的只是"两个线程可以并行"—— 而导入是单张串行的，并行度为 0。

**四处接线，每处都有它非那样不可的理由**：

- `worker/protocol.ts`：新增 `{t:'decode'}` 与**两种**响应 `decoded` / `decode-error`。
  这条分叉是本片唯一的设计要点，写在协议文件头：**解码失败绝不能与"通道坏了"共用
  `error`**。混用的后果是导入一张网页下载的渐进式 JPEG 就把整条渲染链**永久**拖回主线程
  —— 一个用户的坏文件变成全局性能事故。
- `worker/engine.ts`：`decodeJpeg` 作为**注入依赖**进来（与 `createTextRenderer` 同构），
  引擎保持"纯 `handle(request) → response | null`"，Node 里可直接测线程外的全部逻辑。
- `worker/render-worker.ts`：`import { decodeJpeg } from 'app://io/index.js'` —— 绝对 URL，
  正是序3 那条实机回归的教训；`worker-graph.test.ts` 当场把关（改回 `@photo/io` 立刻判红）。
  解码结果与渲染结果同走 transfer list：24 MP 是 96 MB，这里少一次拷贝不是优化是必需。
  字节方向则是**复制**（结构化克隆）—— 调用方在解完之前还要留着那份文件字节。
- `worker-port.ts`：`RenderPortSetup.decodeJpeg` 是"走不走 Worker"的**唯一**决策点。
  刻意不把判断放进 `image-io.ts`：那样"Worker 起没起来"会同时存在于两处（端口降级 +
  导入路径），运行期降级时两边必然不一致。端口内部：`WorkerDecodeError` 原样抛给调用方，
  其余异常（`postMessage` 抛、端口被销毁）→ 降级 + 就地重解，**用户拿到的仍是正确像素**。

**"两端逐字节同源"为什么不受影响**：两条路跑的是同一个 `decodeJpeg`，搬的只是线程。
断言因此照旧成立（引擎侧、端口侧各一条逐字节）。

| 条件 | 状态 | 说明 |
|---|---|---|
| **N1** 机制 | 达成（离线） | 引擎解出的像素 == 主线程 `decodeJpeg` 逐字节；端口解码经 Worker 往返一次，`degraded` 保持 false |
| **N2** 错误通道分离 | 达成（离线，含变异验证） | 截断码流 → `decode-error` + 端口**不**降级 + 后续解码仍走 Worker。变异：把 `WorkerDecodeError` 也送进 `fatal()` → 该条立刻红（只有这一条红） |
| **N3** 失败只降级 | 达成（离线） | 专门在 `decode` 上断掉的假 Worker → 降级 + 像素仍逐字节正确 + 给出人话原因；解码途中 `dispose()` → 挂着的请求被叫醒并就地解完，不永久 await |
| **N4** 界面线程真的被让开 | **未验证** | 单测里的 `FakeWorker` 是同线程同步执行的 —— "在不在另一条线程上"这件事，离线测试**原理上**看不见。判据已写进冒烟：新增一条"导入的 JPEG 确实经端口交给 Worker 解码"，三个条件合一（经过端口 > 0 次 + 端口是 worker + 全程未降级）。桌面入口 `renderer/app.ts` 那行接线本身没有单测闸门，只有冒烟能证明 |

**还留下什么代价**：解码**速度**没变，还是那份同步 JS 内核（比 libjpeg-turbo 慢一个量级
这个事实一条代码也没改）；变的是它不再占用界面线程。以及 Worker 若起不来，仍然静默回到
今天的行为 —— 慢，但正确，且 `degraded` 会露出来。

### 3.5 序 4 · p1 缓存与内存自适应 + 分块调研结论

- 快照预算从**固定 128 MB** 改成随（输出像素数 × 阶段数）推导，且**不得越过内存预算**——
  与 `gateExport` 共用同一套预估与 `SAFETY = 2.0`，一个做准入、一个做预算分配，两处不能各说各话。
- bench 加一条门：**第二次渲染复用阶段数 == 0 即报警**（今天默认路径就是这个状态）。
- **并入 P6-d 序8 遗留（条件 M）**：PNG/JPEG 分块流式编码的可行性 + 代价**结论一份**，只出结论不实现。

| # | 条件 | 怎么验 | 严重度 |
|---|---|---|---|
| **M1** | 24MP 重配方第二次渲染 | 复用 ≥ 6/8 阶段、耗时回到 ~2 s 量级（基线见 `ARCHITECTURE.md` §5.4） | P1 |
| **M2** | 不越预算 | 小预算机器（`PHOTO_MEMORY_BUDGET_MB` 压低）下自适应不得顶破准入线 | P1 |
| **M3** | 分块调研结论文档化 | 明确"做/不做/何时做"，含编码器改造代价 | P2 |

**落地（2026-09-24）** —— 一句话：**"该留几张快照"从外壳里写死的一个字节数，改成内核按本次计划推导。**

- `pipeline/memory.ts` 新增 `cacheBudgetFor({plan, memoryBudgetBytes})`：
  `reserved = 无缓存执行峰值 × SAFETY(2.0)`，`maxBytes = 预算 − reserved`，
  `snapshots = clamp(floor(maxBytes / 单张快照字节), 0, 阶段数)`。于是缓存**只能用准入判断剩下的那部分** ——
  两个函数共用同一份 `estimateMemory` 与同一个安全系数，"准入说这张要 1.3 GB、缓存另外认领 128 MB"
  那种各说各话在结构上不再可能。
- 硬不变量：`reserved + maxBytes ≤ 预算`。**0 张是合法结果**，且会写进 `reason`
  （"预算连执行峰值那一口都不够 ⇒ 一张都不留，宁可慢也不越线"）—— 小内存机器上"缓存主动让位"
  这件事第一次变得**可见**，而不再是静默的复用为 0。
- 三处写死的 128 MB 全部改名并删除：`RenderCacheOptions.maxBytes` → `memoryBudgetBytes`，
  协议 `init`、`worker/engine.ts`、`worker-port.ts`、`session.ts`、`smoke.ts` 各自那份本地常量一并去掉。
  端口未注入预算时**显式发出内核默认值**（而不是"什么都不发"）：Worker 侧与降级后的内联侧必须看到
  同一个数，否则"运行期退回主线程"会顺手改掉缓存策略，把复用差异伪装成线程差异。
  顺带修掉一个藏在那儿的缺陷：`applyBudget` 里 `&& used > 0` 的逃逸口让"预算 0"照样留住 1 张快照。
- **少一次徒劳拷贝**：预算推导出 0 张之后，"每个阶段先克隆满、再整批丢掉"就成了纯浪费
  （24 MP 一次渲染 = 8 × 98 MB）。现在先推导、再按 `阶段数 − 张数` 只克隆真正留得住的末端几张。
  同一档场景改前改后各跑一遍：进程高水位 **1706 → 1525 MB**（−181 MB；比"8 张快照"的直觉值小，
  因为分配器会把刚释放的页接着用 —— 但那是**实测少掉的**，不是推算的）。

| 条件 | 状态 | 证据（本机 24 MP 重配方，一场景一进程） |
|---|---|---|
| **M1** 默认路径真有复用 | 达成 | 第二次渲染复用 **6/8** 阶段，12.8 s → **1.92 s**（6.7 ×）。bench 新增的**复用门**只管这一档：复用 0 即 `exit 1`，改前改后各跑一遍完整 bench，两遍都过 |
| **M1 附带** 小预算档 | 达成（符合设计） | 128 MB 与 1024 MB 两档现在都推导出 **0 张** ⇒ 复用 0。这不是回归：无缓存执行峰值 654 MB × 2 = **1308 MB**，1 GB 预算本来就**装不下**一次这样的渲染，再留缓存就是越线。旧数字（手工把快照预算提到 1024 MB → 复用 6/8）换算过来是"峰值 654 + 快照 784 ≈ 1.4 GB"—— 那个复用率正是越过 1 GB 这条线换来的 |
| **M2** 不越预算 | 达成（离线，含变异验证） | 单测在 4096/2048/1024/512/128/32/8 MB 七档上扫 `reserved + maxBytes ≤ 预算`，并断言 `gateExport.projectedBytes === reservedBytes`（同源的直接证据）。变异：把 `cacheBudgetFor` 里的 `× SAFETY` 拿掉 ⇒ 该条立刻红。实测同向：小预算两档进程高水位 1706 → **1524 MB** |
| **M3** 结论 | 达成 | 见下 |

**M2 没覆盖到的部分（写清）**：桌面端**至今没有任何一处注入预算** —— `EditSession` / 端口都留了
`memoryBudgetBytes` 选项，但 `renderer/app.ts` 不传，于是全走内核默认 2 GB。"小内存机器"目前只有
CLI 的 `PHOTO_MEMORY_BUDGET_MB` 与外壳选项两条入口；**按设备物理内存自适应注入是后续项**，不在本片。
另外 `smoke.ts` 因本片删掉两处本地常量（老的 `cacheBytes` 对那个 Worker 端口**本就是 no-op**，
预算一直跟着端口走）—— 冒烟脚本改过就得重跑一次才算数，离线这边只证明了它能编译与类型检查。

**M3 · PNG/JPEG 分块流式编码：结论 = 不做**（本轮以及可预见的下一轮都不做）。三条理由按分量排序：

1. **天花板太低。** 分块能省的是编码侧的中间缓冲（24 MP 的已过滤扫描线 72 MB、一次全量压缩输出、
   `ByteWriter.finish()` 的整份副本），**省不掉输出像素本身** —— 内核的产物是一整块 `PixelBuffer`，
   24 MP 就是 96 MB，而它必须先完整存在才有文件可写。实测：同一张 24 MP、同一份像素，
   PNG 档进程高水位 465 MB、BMP 档 299 MB ⇒ 差值 166 MB 就是"编码侧全部可挤掉的水份"的上限，
   而同一场景**渲染侧**是 1.5–1.8 GB。**峰值的大头在渲染，不在编码。**
   真要降峰值就得把渲染条带化，而那要改阶段算子本身：`enhance` 里锐化是 3×3（上下各 1 行邻域）、
   去雾是一次**大半径低通**（`boxBlur`，半径 = `max(4, min(w,h)/60)` ⇒ 24 MP 上约 67 行，每条带要重叠
   两倍半径的边界行）；`grain` 是**一条固定种子（1234567）的全局随机序列**按图幅决定撒点数、点落在全图
   任意位置 ⇒ 想按条带独立重放，得先能"跳到序列的第 k 步"，而现在这个 RNG 做不到。
   那是一个数量级的改造，不是编码器的改造。
2. **契约代价大于收益。** `ImageCodec.encode` 返回 `Uint8Array`，三个调用点全依赖"整份字节在手"：
   CLI 写盘、桌面壳把 bytes 交给主进程、冒烟里逐字节比对。改成 sink（`encodeTo(image, sink)`）
   要把 io 注册表 / CLI / 桌面 IPC 同时改，而**桌面这一侧最贵**：渲染在 Worker，字节要跨线程再跨进程
   才落盘，`postMessage` 与 `ipcRenderer.invoke` 都没有"半个文件"的语义 ⇒ 流式意味着自造一套
   分块协议 + 背压。这与支柱 C"降级只换执行体、不换结果"直接顶牛：分块协议每多一处出错机会，
   就多一处**静默碎图**的可能（项目红线）。
3. **JPEG 那一半是"先有再谈"。** 项目**没有 JPEG 编码器**（§4 已明确不做编码）。技术上 baseline JPEG
   反而比 PNG 更适合流式（逐 MCU 行独立、标准允许 restart marker），但那要先回答"要不要自研 JPEG
   编码"这个更大的问题，分块只是它的附属决策 —— 把 M3 当成"分块决策"来处理会掩盖真正待决的那件事。

**若将来做，从这里起步（PNG 侧的既有事实）**：规范**允许多个 IDAT 分块**，所以分块写出是合法 PNG，
不需要任何 hack；本项目编码一律用滤波器 0（None），每行只依赖当前行 ⇒ 逐行产出天然成立；
且当前 `pushChunk` 会为算 CRC 复制一份 `4+data` 的缓冲，分块之后这份额外复制反而消失。

**重新评估的触发条件**（任一成立即重开）：① 出现"单张输出必须超过内存预算"的真实需求
（100 MP 全景、拼接直出）；② 渲染侧完成条带化（那时编码 sink 是顺路的）；③ 决定自研 JPEG 编码器
（那时逐 MCU 流式是默认设计，而不是事后改造）。

**还留下什么代价**：

- 预算推导发生在**执行之前**，用的是 `estimateMemory` 这个"像素管线下界"（§5.4 读出来的第三件事）——
  所以留几张是**保守估计的结果**，宁可少留。这不是缺陷，是刻意的方向：越线一次的代价（进程被系统
  杀掉、半张图）比少复用几帧贵得多。
- **一个未归因的现象（诚实记下）**：复用 0 的两档，第二次渲染仍比第一次慢（+11% ~ +37%）。
  原本猜是"克隆完再丢掉"的开销，把那次徒劳拷贝去掉后**症状依旧** ⇒ 猜错了。
  现在的候选解释是同进程第二次大渲染的 GC / 页表代价（`runCache` 里第一次的结果还被变量持着）。
  没有归因就不写进结论，也不据此调参数。默认路径不受影响（那里第二次快 7.5 倍）。
- 绝对耗时**本机抖动很大**（同一档今天两次跑出 15.1 s / 9.0 s），所以 M1 的判据用"复用阶段数"
  这条与机器无关的量；这也符合 §5.4 那条自我修正教训：**能相减的量必须同源同状态**。
- 老的"快照预算"参数彻底没了 ⇒ 任何想手工调快照张数的做法都只能改成调**内存预算**这一个入口。
  这是本片要的收口，但对方程式用法（`PHOTO_MEMORY_BUDGET_MB` 之外的期望）要提前说清。

## 5. 回归要求（每项必留）

1. **逐字节一致仍是主断言形态**，但**必须先划清它的适用边界**——这是本轮最容易自欺的地方：
   - 同一份**已解码像素**进内核 → 出图，跨端必须**逐字节一致**（内核的责任，历来如此）。
   - **不同解码器**之间做不到逐字节一致：JPEG 色度上采样与取整在各实现里有合法差异。
     故 C2 的口径固定为「**尺寸/边界严格一致 + 亮度 / 色度 / 全图均值三条白名单容差**」，
     并把该容差写进测试名与文档，**不许将来偷偷把它升格成"逐字节"**。
     <br>**序3 实施时按用户裁定改过一次路线**：原计划让桌面继续用 `createImageBitmap`
     解 JPEG、只把比对容差写明白；改成**桌面也用内核解码器**之后，跨端同源变成可逐字节
     断言的事（两端 == 同一个 `decodeJpeg`），容差那条只留在"内核 vs Chromium 独立参照"
     这一处。原口径里那句"**像素多重集严格一致**"随之**从 C2 撤下** —— 两个独立实现
     的像素多重集本来就不会相等（各自的取整把同一个像素散到邻近值上），
     它只在"同一份已解码像素进内核"这一侧成立，而那一侧本来就是逐字节。
   - **"在哪条线程上跑"不在逐字节断言的覆盖范围内**：单测里的 `FakeWorker` 是同线程
     同步执行的，像素照样逐字节一致（序3.5 的 N4 因此只能落进真渲染进程的冒烟）。
     凡是"跨线程 / 跨进程"性质的断言，离线门**原理上**看不见 —— 与 §3.4.1 那条
     Worker 模块图回归是同一类缺口，别再用"测试全绿"回答它。
2. **朝向是新增的第三条同源断言**：X1（桌面 vs CLI）与 X2（1..8 枚举）缺一不可。
3. **工程文件**：D1 往返保真 + D2 坏文件收敛 + D3 不含像素，三条都进内核测试，不放壳。
4. **功能对齐项照旧**：#31/#32/#4 每项**附一条真实 Electron 渲染 smoke 断言**（清单在 `apps/desktop/electron/main.cjs`）。
5. **壳里仍不许出现像素算法**。一旦发现"壳里必须算点像素"，停手补内核。
6. **"缓存到底有没有在工作"必须有一条自动闸门**：那个老缺陷（默认预算下 `复用 0/8`）在 P6-d
   是靠人**读 bench 报告**才发现的 —— 它不改变任何一个像素、不报任何错，没有闸门的话可以在
   代码里安静住上一年。现在两条互补：内核单测管**推导对不对**（`reserved + maxBytes ≤ 预算`，
   跨 7 档预算扫），`npm run bench -w @photo/cli` 的**复用门**管**真实大图上有没有生效**
   （默认预算那一档复用阶段数 == 0 即 `exit 1`）。
7. 台账改动**同步统计**；状态只在代码真跑通后才改。`npm run verify` EXIT=0 才算完成，一序一提交。
