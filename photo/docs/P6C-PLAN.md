# P6-c · 最小桌面壳 —— 里程碑定义与验收

> 本文回答两件事：**legacy 怎么冻**、**P6-c 做到什么程度算赢**。
> 目的很功利：让「新内核」从一个"证明得了架构、却没人能用"的成果，
> 变成一个**能双击、能导入、能出图**的产品。在此之前，所有测试都是账面上的。

---

## 1. 为什么要单独定义这个里程碑

截至 P6-a / P6-b 结束，仓库里并存着**两套代码**：

| | `legacy/`（v0.11.0） | `packages/* + apps/cli`（新内核） |
|---|---|---|
| 用户能用吗 | ✅ 能双击、能出图 | ❌ 只能 `node` 跑命令行 |
| 架构对吗 | ❌ 四条病根都在 | ✅ 病根 1/4/5/6 已关闭 |
| 测试 | 无 | 304 个用例（core 181 / io 17 / cli 106） |
| 维护成本 | 修 bug 只能打热修 | 改一处、四处受益 |

**两套代码并存的每一天，维护成本都在涨。** 而"测试全绿"这件事本身
不产生用户价值 —— 288 个测试测不到一次真实点击。所以 P6-c 的定位不是
"再做一个里程碑"，而是**把已经做对的内核接上一个能被使用的壳**。

### 一个必须先说清的事实

新内核**不缺渲染能力**。`packages/core` 里的 `buildPlan` + `executePlan`
已经能产出与 legacy 等价（且更正确）的成品；`apps/cli` 已经用真实的
24MP 图片端到端跑通并写盘。缺的只有三样**平台能力**，而它们按架构约定
本来就该由外壳注入：

| 缺的能力 | 现状 | P6-c 的填法 |
|---|---|---|
| PNG / JPEG 解码与编码 | io 有 BMP/PPM；CLI 侧有 PNG（zlib） | Electron 渲染进程用 `canvas` / `createImageBitmap` / `toBlob` |
| 真实 Worker | `scheduler` 只有端口抽象 | 外壳注入 `Worker` 构造器（浏览器侧天然可用） |
| 文字光栅化 | 只有 `noopTextRenderer` | `canvas.measureText` + `fillText` 实现 `TextRenderer` |

**这三样都不许下沉到 core**（core 的 `tsconfig` 是 `types: []`，写了就编译失败）。
这不是纪律要求，是编译期强制。

## 2. legacy 冻结政策

### 2.1 冻结范围

| 允许 | 不允许 |
|---|---|
| ✅ 修**崩溃**（进程/渲染进程起不来） | ❌ 新增任何功能 |
| ✅ 修**数据丢失**（保存失败、导入丢图） | ❌ UI / 交互改版 |
| ✅ 修**静默错图**（导出的图是错的，且不报错） | ❌ 重构、抽模块、换范式 |
| ✅ 升级**安全相关**依赖 | ❌ 依赖升级（非安全） |
| | ❌ 性能优化 |

判据一句话：**「用户会不会因此丢东西或拿到错东西」—— 会，才修。**

### 2.2 修复流程

1. 先写**最小复现步骤**（legacy 无测试框架，手写清单即可，附截图/文件）。
2. 修**只改必要的那几行**，不顺手清理周边。
3. 在 `legacy/README.md` 顶部记一条 `修复记录`：现象 / 复现 / 改动 / 影响面。
4. 同一现象**在新内核里必须有一个回归用例**（若内核尚无对应能力，则记入待办）。

### 2.3 冻结生效时点

> **P6-c 的首个"可双击版本"产出后，`legacy/` 从主入口降级为历史版本。**

具体动作（都在同一次提交里做完）：
- 根 `README.md` 的"快速开始"从 legacy 指向新壳；
- `legacy/README.md` 加一句显式说明："本目录为 v0.11.0 存档，仅接受致命修复，新功能一律进 `packages/`"；
- 冻结前的最后一个 legacy 版本打 tag（`legacy-v0.11.0-final`）。

## 3. P6-c 里程碑定义

### 3.1 目标（一句话）

> **双击启动应用 → 导入一张真实照片 → 应用一个预设 → 导出成品。**
> 全链路由 `@photo/core` 渲染，外壳只负责"像素从哪来、往哪去"。

### 3.2 验收条件（逐条可验证）

| # | 条件 | 怎么验 | 严重度 |
|---|---|---|---|
| **A** | 双击应用图标能启动，出现工作区 | 手动 | P0 |
| **B** | 能导入 JPEG（含 24MP 大图），显示预览 | 手动；预览长边 ≤ 1400 | P0 |
| **C** | 拖动"亮度"滑杆，预览实时更新 | 手动；松手后 < 100 ms 出画面 | P0 |
| **D** | 应用一个内置预设，预览与参数同步更新 | 手动 | P0 |
| **E** | 导出 PNG，尺寸为**原图尺寸**（非预览尺寸） | 手动 + 核对文件尺寸 | P0 |
| **F** | 导出结果与预览**同源**：同一文档下 `plan` 的阶段序列一致 | 自动：复用 `apps/cli` 的同源断言思路 | P1 |
| **G** | 撤销 / 重做 10 步后，像素回到对应历史节点 | 手动 + 不变量用例 | P1 |
| **H** | 改一个末端参数（如暗角），预览**复用缓存前缀** | 自动：`RenderCache.stats.reused > 0` | P1 |
| **I** | 24MP 预览 + 导出的峰值内存可解释（有实测基线） | 见 `apps/cli/scripts/bench.mjs` 的实测数字 | P1 |

**F / H 必须做成自动化用例**，不能只靠手点 —— 它们正是"预览怎么画的、导出就是怎么画的"
这条架构保证的守门人。把内核已通过的断言搬到壳里再跑一次，成本很低。

### 3.3 明确**不做**的事（防范围失控）

| 不做 | 为什么现在不做 |
|---|---|
| ❌ 移动端（Capacitor） | 属于 P6-d，先证明桌面壳能跑 |
| ❌ 插件宿主 / 开放预设市场 | P7 生态的事 |
| ❌ 多标签工程管理 / 项目文件读写 UI | 内核已有 `PhotoDocument`，壳先跑单图 |
| ❌ 批处理 UI | `apps/cli` 已经覆盖了这个场景 |
| ❌ 视频 / 抠图 / AI 修图 | legacy 有 `video.js`，迁移优先级低于主链路 |
| ❌ "精致 UI"（动效、主题、自定义控件） | **先跑通链路，再谈好看**。这一条最容易吃掉整个里程碑 |
| ❌ 换 Tauri / 换框架 | 决策 D4：保留 Electron。壳要薄，薄到可以随时换 |
| ❌ 为 legacy 加任何功能 | 见 §2 |

### 3.4 架构约束（不可破）

```
Electron 主进程        ← 窗口生命周期、文件对话框
  └─ 渲染进程（薄壳）
       ├─ 注入 CodecRegistry：BMP/PPM（io）+ PNG/JPEG（canvas）
       ├─ 注入 TextRenderer：canvas.measureText / fillText
       ├─ 注入 Worker 构造器：真实 Worker 适配 scheduler
       ├─ 持有 PhotoDocument + RenderCache（交互式预览）
       └─ 调 @photo/core 的 buildPlan / executePlan
```

- 壳里**不许**出现任何像素算法（模糊、曲线、HSV……）—— 一律走内核。
- 壳里**不许**自己拼 `Op` 对象给内核；一律走 `doc.pushOp`，用户输入若有 JSON
  入口则复用 `apps/cli/src/recipe.ts#normalizeOp`（见 ARCHITECTURE §5.3(b)）。
- 一旦发现"壳里必须算点像素才好使"，停手 —— 那说明内核的抽象缺了一层，
  该补的是内核。

### 3.5 任务拆分（建议顺序，每步都可独立验证）

| 步 | 内容 | 完成标志 |
|---|---|---|
| c1 | Electron 骨架：主进程 + 渲染进程 + 双击启动 | 验收 A |
| c2 | 打开文件对话框 + `createImageBitmap` 解码 → `PixelBuffer` | 能打印导入图的尺寸 |
| c3 | 预览：`buildPlan(PREVIEW_TARGET)` + `executePlan` → 画到 canvas | 验收 B |
| c4 | 参数面板（先只放亮度/对比/饱和/暗角四根滑杆）+ `pushOp` | 验收 C |
| c5 | 预设下拉 + `applyPreset` | 验收 D |
| c6 | `RenderCache` 接入预览循环 | 验收 H |
| c7 | 导出：全尺寸 `buildPlan` + PNG 编码 + 保存对话框 | 验收 E |
| c8 | 撤销/重做按钮 + 键盘快捷键 | 验收 G |
| c9 | 把 F / H 做成自动化用例 | 验收 F / H |
| c10 | 冻结 legacy（§2.3 三件事） | 根 README 指向新壳 |

## 4. 端到端冒烟 checklist（P6-c 验收时手写执行）

> 每一条都要给出**可观测的结果**，不接受"看起来正常"。

### 4.1 启动与导入

- [ ] 双击应用 → 出现窗口，无白屏、无控制台报错
- [ ] 导入一张 24MP JPEG → 预览出现，长边 ≤ 1400
- [ ] 导入一张 320×240 的小 BMP → 预览不拉伸变形
- [ ] 导入一个损坏的 PNG → **明确报错**，不是静默空白

### 4.2 编辑与预览

- [ ] 拖亮度滑杆到 150 → 画面变亮；松手后画面不再抖动
- [ ] 拖亮度滑杆到 50 → 画面变暗（**不是全黑** —— 全黑说明稀疏参数漏进了内核）
- [ ] 连拖 20 次亮度 → 按一次撤销回到拖之前（`merge` 语义生效）
- [ ] 旋转 90° → 画面宽高互换，内容不被压扁
- [ ] 应用预设 → 参数面板数值与画面同时变化
- [ ] 改暗角 → 画面更新耗时明显短于"从头渲染"（缓存命中）

### 4.3 导出

- [ ] 导出 PNG → 文件尺寸 = 原图尺寸（不是 1400）
- [ ] 导出的图与预览**观感一致**（同一份计划，同一套执行器）
- [ ] 导出到与源图同名的路径 → **被拒绝**并提示（复用 `findOutputCollisions` 的思路）

### 4.4 健壮性

- [ ] 编辑过程中拔掉输入文件所在磁盘 → 不崩溃
- [ ] 撤销到最初始状态 → 画面 = 原图（逐像素）
- [ ] 反复导入/导出 30 次 → 内存不单调增长（`RenderCache` 有预算裁剪）

| 风险 | 对策 |
|---|---|
| 壳越写越厚，"薄壳"变成第二个 legacy | §3.4 三条禁止 + 代码评审只看"有没有像素算法" |

### 6.2 一个必须记住的架构决定：结构化对象 ≠ 宿主对象

外壳的 `surface.ts` 刻意**不**依赖 `CanvasRenderingContext2D`，而是定义一组结构化
窄接口 —— 目的是让业务逻辑（session / 文字栅格化 / 编解码）能在 Node 里配假画布
跑完全链路，F / H 才能自动化。

代价是踩到一个**假画布结构上无法暴露**的坑：

| 症状 | 真因 | 修法 |
|---|---|---|
| `putImageData` 抛 `parameter 1 is not of type 'ImageData'` | 真 Canvas 只接受**同 realm 的 `ImageData` 实例**，而内核传的是 `{width,height,data}` 结构化对象 | 把"结构化像素 → 原生实例"的转换收进**画布层**（`DrawableSurface.putPixels` / `readPixels`），业务层因此完全不需要知道 `ImageData` |
| `drawImage` 抛 `The provided value is not of type '(CSSImageValue or … ImageBitmap …)'` | `decodeBitmap` 把真实 `ImageBitmap` 包成了 `{width,height,close}` 普通对象 | 直接返回真实 `ImageBitmap` |

这两条**单元测试永远测不出来**（假画布结构匹配），只有真实 Electron 渲染进程才能
发现。它们正是冒烟测试存在的理由，也是 §3.2 里"把 F / H 做成自动化"与"跑冒烟"
两件事**不能互相替代**的具体证据：

> 单元测试证明"逻辑对"；冒烟证明"这套逻辑真的接在 Chromium 上能跑"。

### 6.3 冒烟自检（`npm run smoke`）

`--smoke` 模式起一个隐藏窗口加载 `smoke.html`，在**真实渲染进程**里跑 21 项检查，
再由主进程拿内核的 `SHELL_REQUIREMENTS` 逐条核对窗口实际配置。

检查分三层，缺一不可：

| 层 | 例子 | 回答的问题 |
|---|---|---|
| 链路 | 冷启动 / 全复用 / 复用==重算逐字节 / 预览==导出逐字节 | 内核在这台机器上算得对吗 |
| 平台 | 真实 Canvas 文字栅格化改了像素 / PNG 编码→解码往返逐字节还原 | 平台能力真的通吗 |
| 外壳 | **加载正式页面 `index.html`** 并点一次示例图 / preload 桥注入 / 无 console 错误 / 窗口配置逐条核对 | 产品**打不开**吗、配置错了吗 |

第三层是刻意加的：前面两层跑的是 `smoke.html`，它证明不了正式页面能开。
import map 写错一个字、`app.ts` 里选择器拼错，界面白屏而自检照样全绿 ——
"产品打不开、自检很绿"这种落差必须堵掉。

### 6.4 受限环境下的运行说明（诚实边界）

无头 / 容器 / 受限沙箱环境里 Chromium 起不来，症状是**一行输出都没有**（不是报错）。
冒烟与截图模式因此会自动加两个开关：

- `--disable-gpu`：没有可用 GPU 时 GPU 进程反复崩溃，最后 `FATAL: GPU process isn't usable.`
- `--no-sandbox`：受限环境里 OS 级沙箱无法初始化 → **渲染进程起不来**。

> **这条边界的诚实说法**：`--no-sandbox` 关的是 **OS 级沙箱**；自检里
> `webPreferences.sandbox` 核对的是 **Electron 的渲染沙箱偏好**。
> 两者相关但不是一回事 —— 绿报告**不构成**"OS 沙箱已启用"的证据，
> 因此冒烟启动时会打一条 WARN 明说这件事。
> 想要严格模式设 `PHOTO_SMOKE_STRICT_SANDBOX=1`。

另一个环境坑：`ELECTRON_RUN_AS_NODE=1` 一旦被设，`electron` 退化成纯 Node，
窗口不建、preload 不跑。`scripts/smoke.mjs` / `shot.mjs` 会显式删掉它再启动。
